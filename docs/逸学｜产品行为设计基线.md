# 逸学｜产品行为设计基线

## 1. 设计对象

产品行为设计回答：

> 在一个真实使用场景中，用户做了什么之后，逸学应该发生什么；相关信息如何产生、变化和被使用；用户如何参与、感知、确认或修改。

流程、信息流和交互不是三个串行阶段，而是同一场景的三个视图：

- **行为视图**：系统做什么；
- **信息视图**：信息如何产生、变化和流动；
- **交互视图**：用户如何触发、看到、确认、修改和纠偏。

后续以真实 `Use Case` 为基本单位，同时设计这三个方面。

## 2. 当前设计边界

本阶段设计真实 `Use Case` 中的**系统行为、信息变化、用户交互及异常处理**。

不进入数据库、API、Agent、Prompt、Context Processor、RAG、检索、代码结构、部署及完整视觉规范等 Solution Design。

现有 Problem、Vision、Boundary、Principles 和各域 Model 是上位约束。只有真实场景证明现有 Model 无法表达必要行为时，才回头调整 Model。

## 3. 产品与交互设计原则

### 3.1 流程最小化

以完成用户目标所需的最少步骤完成任务；没有明确收益，不增加额外确认、填写、跳转或维护。

### 3.2 信息最小充分

只呈现完成当前任务所需的信息与操作，避免无关元素和层级造成失焦。

### 3.3 渐进呈现

复杂能力按需暴露，次要信息、高级能力和历史内容不默认占据当前注意力。

### 3.4 行为一致、结果可预期

相同对象和操作保持一致语义，用户能够预判操作结果。

### 3.5 错误低成本可恢复

误操作、AI 判断错误或用户改变决定时，应尽量能够低成本恢复；可撤销时优先撤销，仅对高风险且难恢复的操作增加确认。

### 3.6 简洁不等于简陋

减少流程和元素，不牺牲信息层级、排版、间距、反馈和整体视觉品质。

目标是：

> **克制而完整，而不是粗糙的工程 Demo。**

## 4. 旧项目提供的反面约束

旧版已经验证：

- 页面和步骤增加不等于形成信息闭环；
- 保存信息不等于后续真正使用；
- 界面显示的状态不等于系统真实状态；
- 功能完整度不等于用户体验质量。

因此：

> **不得把系统自身的复杂度转嫁给用户。**

## 5. 设备策略

MVP 采用**单版本、桌面优先、响应式适配手机**；核心行为和信息语义跨设备一致，手机端至少保证核心任务不被阻断。

## 6. 后续讨论方式

不先设计完整总流程，而是逐个讨论真实 `Use Case`：

1. **场景起点**：用户为什么进入逸学，做了什么；
2. **系统行为**：逸学应该做什么、不应该做什么；
3. **信息变化**：读取什么、产生什么、修改什么、什么不保存；
4. **用户交互**：用户看到什么，在哪里确认、修改、拒绝或纠偏；
5. **异常与设备检查**：出错、反悔、删除、失效时怎么办，手机端是否存在任务阻断。

只有具体场景证明现有 Model 无法表达必要行为时，才回头调整 Model。
