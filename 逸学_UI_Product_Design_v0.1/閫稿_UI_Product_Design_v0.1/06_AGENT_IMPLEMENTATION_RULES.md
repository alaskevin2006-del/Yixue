# 逸学｜Agent Implementation Rules

## 1. 工作方式

不要一次性“重做整个站点”。

固定流程：

```text
选一个页面
→ 读取 Product Design + 对应 Use Case + Page Spec + Visual Design
→ 列出当前实现与规范的差异
→ 只修改本页及必要公共组件
→ 截图
→ 按 Visual Acceptance 自检
→ 修正
→ 人工验收
→ 冻结本页
→ 下一个页面
```

未验收页面不得因为后续重构被顺手重新设计。

## 2. 修改前必须回答

在开始编码前，Agent 必须先内部确认：

1. 这个页面的唯一主任务是什么？
2. 哪个区域是主视觉中心？
3. 哪些信息必须常驻？
4. 哪些信息只能按需出现？
5. 本次修改是否会改变产品行为，而不只是视觉？

若第 5 项为“会”，必须先核对对应 Use Case；没有依据时停止自行发挥。

## 3. 严禁自行新增

除非文档明确要求，不得新增：

- 页面；
- Tab；
- 侧栏；
- Card；
- Badge；
- 统计指标；
- 进度/掌握度；
- 解释文案；
- 推荐逻辑；
- 自动状态更新；
- 新的资料分类；
- 新的产品概念。

“看起来更完整”不是新增理由。

## 4. 现有代码不是产品依据

如果现有组件结构与 Page Spec 冲突：

- 优先改组件结构；
- 不得为了复用组件而改变信息层级；
- 不得因为某组件已存在，就把它保留在页面上；
- 删除错误 UI 比给错误 UI 换皮优先。

## 5. 不确定时的处理

当设计文件没有定义某个行为：

1. 保持最小；
2. 不扩展；
3. 不推断完整业务流程；
4. 将该点列为待确认问题。

不得用通用 SaaS 经验自动补全逸学。

## 6. 视觉实现规则

- 先统一全局 token，再改局部；
- 不用局部 hardcode 修补整体设计问题；
- 组件复用必须保持同一语义；
- 一个组件若在不同页面承担不同心理模型，应拆分而不是强行共用；
- 不以“大圆角 + 阴影 + 浅绿色背景”作为默认美化手段。

## 7. 每页完成后的输出

Agent 应给出：

```text
本页修改了什么
仍未解决什么
是否改变产品行为：是 / 否
对应截图
Visual Acceptance 未通过项（若有）
```

避免输出大段自我评价；人工验收以页面结果为准。
