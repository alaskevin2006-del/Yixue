# 逸学｜Product Design

## 1. 产品心智

逸学不是完整课程平台，也不是学习 Dashboard。它服务用户原本正在发生的真实学习，在用户需要资料、当前答疑、回顾过去学习或判断下一步行动时按需介入。

因此，产品设计的核心不是“把系统拥有的信息展示完整”，而是：

> **在当前任务下，只让用户看到足以完成当前任务的信息与操作；其他信息按需出现。**

## 2. 顶层入口与职责

### 2.1 首页：行动判断与近期安排

首页回答的是：**我现在/今天怎么推进？**

主要承载：

- 当前日/周时间视图；
- 用户已有安排；
- 用户通过自然语言补充当前变化、意图或约束；
- AI 结合必要的 `Subject State` 给出行动建议；
- 需要形成具体日程时，先显示候选，再由用户采用。

首页不承担：

- 学科知识问答；
- 维护 Learning Memory Item；
- 维护公共/私人资料；
- 自动根据日程或完成情况修改 `Subject State`；
- 完整 Todo、人生事务或长期项目管理。

### 2.2 资料库：公共资料与投稿

资料库回答的是：**我要找一份课程资料，或提交一份资料。**

主要承载：

- 公共资料按实际课程组织；
- 课程/资料搜索；
- 课程内辅助筛选；
- 资料投稿及审核状态。

资料库不承担：

- 学习状态展示；
- 根据学习状态主动推荐资料；
- 学习问答；
- 私人学科资料管理；
- “最近活跃”“掌握度”等学习信息。

### 2.3 学科空间：一个学科的持续学习上下文

学科空间回答的是：**我正在这个学科里学习。**

一级局部导航固定为：

```text
学习 / 回顾 / 资料
```

其中：

- **学习**：当前 AI 学习对话；
- **回顾**：最近学习、Learning Memory Item 与主动复盘；
- **资料**：该学科的私人资料；
- **现状**：`Subject State` 的按需入口，不作为第四个常驻内容 Tab。

## 3. 跨模块关系

模块可以读取必要信息，但不得因为“有关联”就互相拥有状态。

### 3.1 Subject State

- 每个学科空间只有一份 `Subject State`；
- 首页行动辅助可以读取它作为参考；
- 首页日程、AI 建议和过去安排不会自动修改它；
- 更新必须来自用户主动提供的新现状，AI 可以整理成候选，用户确认后才生效。

### 3.2 Conversation 与 Current Context

- 原始学习对话属于对应 Subject Space；
- 当前回答只构造最小充分 `Current Context`；
- 历史对话不因为存在就全部进入当前回答；
- 历史内容属于辅助信息，不常驻占据当前学习界面。

### 3.3 Learning Memory Item

- 默认不沉淀，一次 Conversation 可以产生 0 条；
- 只有对未来学习仍有明确价值的信息才保留；
- 同一个学习点跨对话维护同一个 Item；
- Active / Inactive 只影响默认扫描，不等于“会/不会”的永久判定；
- UI 不把全部学习记忆常驻暴露给用户，需要时在“回顾”中查看。

### 3.4 资料

- 公共资料由资料库组织；
- 私人资料属于对应学科空间；
- 资料不会因为存在就自动进入 AI 回答；
- 用户明确调用资料时，其他能力才使用其内容；
- 公共资料与私人资料的进一步引用机制若未在当前设计中定义，Agent 不得自行新增。

## 4. 全局产品行为模式

### 4.1 AI 的“建议”与用户的“状态”分离

凡 AI 输出会改变用户之后看到或依赖的状态，应先作为**候选**存在。

当前已明确的候选模式包括：

- 候选日程；
- Subject State 建议更新；
- Learning Memory Item 候选。

候选必须：

1. 与已生效状态视觉可区分；
2. 用户可编辑、拒绝或继续调整；
3. 未采用前不得伪装成已保存事实；
4. 采用后才进入对应权威状态。

### 4.2 页面 / 抽屉 / 局部展开的分工

- **独立页面或页面状态**：当前主任务已经改变，例如从“学科学习”进入“复盘会话”。
- **抽屉**：用户仍在当前主任务中，只需要临时查看或修改辅助信息，例如历史对话、学习现状。
- **局部展开**：只影响当前局部对象，不需要制造新导航层级。

不得因为实现方便，把所有辅助信息做成常驻侧栏。

### 4.3 默认不打断

系统不应在每次对话、每次离开页面、每次安排变化后强制用户复盘、确认或填写信息。只有当用户主动进入相应任务，或某项高价值变化确实需要用户确认时才出现操作。

## 5. 信息呈现原则

### 5.1 一个页面一个主要视觉中心

页面应首先让用户明确“现在主要在做什么”。辅助信息弱化、折叠或按需出现，不与主任务争夺注意力。

### 5.2 不用 UI 替系统复杂度背书

不得为了体现“功能丰富”而新增：

- 无明确任务价值的统计；
- Badge；
- “最近活跃”；
- 掌握度；
- 大段解释文字；
- 重复标题；
- 多层卡片嵌套。

### 5.3 不自行补全未定义行为

视觉稿出现但产品语义未定义的按钮、菜单或文件动作，只能保留轻量占位或暂不实现；不得由 Agent 自己发明业务逻辑。

## 6. 当前 MVP 主要 Use Case

1. 用户在首页说明今天/当前变化，获得并调整行动安排；
2. 用户查看、纠正某学科 `Subject State`；
3. 用户在学科空间进行当前学习答疑；
4. 用户主动回顾近期学习并确认值得保留的 Learning Memory Item；
5. 用户查找公共课程资料；
6. 用户提交资料等待审核；
7. 用户管理某学科的私人资料。

具体行为见 `use-cases/`。
